# Implementation plan

From a one-mechanic game to the adaptive learning spec (v0.1, 2026-11-17, written for the early years; "Technical design specification": ontology, seeded items, mechanics, evidence, learner model, scheduler, P0 to P5 roadmap). The full plan, with the gap analysis and the decisions it needs, was written 2026-11-22 with the owner; this is its working copy. Section numbers (§) are the spec's.

Scope (decided 2026-11-23): every school year and ability, starting with the earliest skills but not limited to them. Progression is by ability, not age: the skill graph's prerequisites and the learner's evidence decide what comes next; curriculum stages (EYFS, KS1 to KS4) are labels mapped onto skills, never gates; placement is by probes; no age, birth date or year group is stored.

## Where Flashtap stood (0.1.9)

One mechanic (tap one of N pictures), five unseeded round types, no learner state, a points-and-streak score, in the browser only. Bugs against §9: Colours could offer two right answers, Counting hung above ten choices, every tile printed its own name (so Letters and Colours were reading tasks), Letters mixed /k/ and /tʃ/ under C, and sentences were built from string templates ("How many Sheeps").

## PRs

1. **Migrate (0.2.0, done).** python-app-template shape; seeded, checked rounds in Python with the five bugs fixed; `GET /api/round`; Play and Settings on strata-react; no score or streak.
    - Exit: property tests over thousands of seeds per mode find exactly one right option, and the same seed gives the same round.
2. **P0 ontology seed (0.3.0, done).** `src/flashtap/packs/` as versioned TOML (not YAML: `tomllib` is in the standard library, so no new dependency) with pydantic models ([content.md](content.md)): skills, parameter dimensions, typed edges with provenance (§3), misconceptions, curriculum objectives. The schema covers every school year (skills, not ages; stages only as curriculum labels); the first slice to fill it is the earliest skills: maths counting, cardinality, subitising 1-5, numerals 0-10, more/fewer; literacy letter forms, initial sounds, Phase 2 GPCs (s a t p i n m d). `flashtap content check` refuses dangling edges and `prerequisite_strong` cycles. An adult Content screen.
    - Exit: every EYFS maths and literacy Early Learning Goal is mapped or marked out of scope, and a skill from a later stage can be added without a schema change.
    - Done: 44 skills over 3 domains and 20 strands, 52 typed edges, 9 misconceptions, Letters and Sounds Phases 2 and 3 (51 GPCs), 71 words with their sounds (the old `lexicon.py` tables moved here); 15 EYFS goal statements, 12 mapped and 3 set aside (retelling, letter formation, free writing); a test adds a Key Stage 1 skill and objective with no schema change. Every pack is a draft until reviewed: the IPA and segmentations by a phonics teacher, the edges marked `src.flashtap_judgement` by someone who teaches early maths and reading.
3. **P1 mechanics (0.4.0, done).** Templates declare Q-matrix roles (§7, §8). Mechanics: select one, match pairs, sort, sequence, give-N, fill missing, brief exposure, audio respond. Distractor generators: near-number, reversal (6/9, 12/21), confusable graphemes (b/d/p/q), phonological neighbour.
    - Exit: every item rebuilds from (template, version, seed); the validator suite over 1,000 seeds per template finds no ambiguous key.
    - Done: 12 templates over the 8 mechanics (`rounds.TEMPLATES`; the 5 original kinds plus Missing number, Quick look, Listen, Give a number, Order, Capitals, Sort by sound), each with a version and its skills as primary, secondary or confound. A round carries (kind, version, choices, seed) and the versions of the packs it drew from (`content`, recorded on every attempt and decision since 0.7.0) and rebuilds from them; another template or pack version is refused, not answered differently. `mechanics.check` covers both families: one tap (one right option, distinct pictures, every wrong option names its generator) and an arrangement (each piece belongs in at most one place, pieces that look alike belong together, every place can be filled). `test_rounds.py` walks 1,000 seeds of every template. The placing board is strata-react's `PlaceBoard` (strata-react PR #285, released as 1.3.0), two taps rather than a drag, because React Aria's drag and drop has no tap-to-hold state for small fingers.
    - Left for later: the confusable and neighbour tables are drafts for the phonics review; a Quick look's 1.5 s is a default, not a measured threshold; isolated sounds came with the voice clips in 0.9.0 (the Sounds round), consonants made pure by strata-models since 0.17.0 (see Decisions).
4. **P2 learner baseline (0.5.0, done).** `strata_python.db`: learners (pseudonymous id plus a nickname; no age, birth date, year group, school or photo), sessions, append-only attempt events keyed by `event_id`, tombstones. Rule and BKT estimators behind one interface (§10); derived reporting states (§13), unobserved kept apart from not mastered. Adult Learner screen with evidence provenance; export and delete (§17).
    - Exit: rebuilding from the event log reproduces identical estimates.
    - Done: `src/flashtap/learners/` (models, store, evidence rules, estimators, report) and its first migration; the server rebuilds each attempt's round and judges the first answer itself; a resent event is acknowledged once, a changed one refused. Estimates are never stored: they are computed from the log on read, so the profile is a rebuild every time, and `flashtap learners rebuild <export>` checks an export's estimates against its own events (a unit test replays 60 attempts, and the same attempts sent in another order, to identical estimates; an integration test does it through a real server and a real `flashtap` process). Play records rounds for the learner chosen in Who is playing; the Learners and Learner screens show each skill's state, BKT beside the rule baseline, and the rounds behind it with why each did or did not count; strike out with Undo, export, delete behind a confirm. With no database configured the records go in a SQLite file beside the settings.
    - Left for later: BKT's prior, learn, slip and guess (1 in the number of tiles) and the state thresholds are first guesses, to be fitted from real attempts in P3; fluency and retention estimates (§10) wait for P3's scheduler, which needs them; overrides by a grown-up (`POST /v1/learners/{id}/overrides`, §15) came in P4 (0.8.0); attempts were sent once from the browser until 0.9.0, which queues them on the device (Offline, below); the deployment still needs its Postgres schema (`strata-db new-app flashtap` and the service's `STRATA_DB_*` environment, see [deploying.md](deploying.md)).
5. **P3 adaptive engine (0.6.0, done).** `POST /api/v1/sessions` and `/next` with rationale codes (§15). Eligibility filters, utility ranking, seeded exploration, logged candidates and probabilities (§12). Placement by probes from the learner's evidence (never from an age), spaced review, diagnostic contrasts, a session length cap and offered breaks. Replay endpoint.
    - Exit: on simulated learners, held-out log loss beats the rule baseline.
    - Done: `src/flashtap/engine/`. The model is BKT over the skill graph's strong prerequisites (closed through skills no round assesses yet): a right primary answer lifts unseen prerequisites, a wrong one caps unseen dependents, so a few probes place a learner; a round is predicted from every skill it names. The policy puts limits first (20 rounds or 15 minutes, a break offered every 10 rounds and after 3 misses running), then weighs one candidate per kind of round, labelled placement probe, introduce, practise, spaced review (a per-skill half-life) or consolidate, set aside for a known prerequisite gap, after 2 misses unless likely to go right, or after the same kind twice; it ranks them by learning, information, retention, enjoyment, frustration, repetition and a diagnostic bonus for a contrast after a miss, and draws by a softmax with 10% uniform, seeded by the session and decision number. Every decision is stored (`decisions` table) with every candidate's components and chance; `/next {seq}` is idempotent; `POST /api/v1/evaluations/replay` and `flashtap learners rebuild` remake each from the log as it stood (receipt and strike times) and name any that differ. Play has "Chosen for them" with the reason shown, break offers and the session's end. On 200 simulated learners (6 sessions each, fitted on 140, scored on 60 held out), the engine's model has log loss 0.522 against the rule's 0.556 (Brier 0.173 against 0.187); BKT without the graph is between, 0.528. Learners played by the engine policy knew 12.8 of 18 skills at the end against 12.5 under a uniform pick.
    - Left for later: the weights, thresholds and caps are starting points to fit from real sessions (each decision's logged chances make an off-policy comparison possible); the cap and break interval became the grown-up's settings in P4 (0.8.0); difficulty within a kind (choices, number range) came as steps of difficulty in 0.11.0 (item 8); the simulation's learners are a model, so its numbers say the code works as designed, not that children learn (P5); retention does not yet change the prediction, only the schedule, until delayed answers say how much is forgotten; transfer probes (§13) came in 0.13.0 (item 10); overrides by a grown-up came in P4 (0.8.0).
6. **P4 engagement, light (0.8.0, in review).** Choice of two activities, a 3-point face rating, hesitation and retry patterns shown as hypotheses (§11), parent session limits; and (from a spec review) a grown-up's overrides of a skill's state with source-labelled evidence (§13, §15).
    - Exit: a short pilot checklist; it needs real sessions.
    - Done: session settings for the grown-up (rounds and minutes in a session, break every, their choice every, ask how it was every; Settings, Sessions tab), which each new engine session takes as its `Config`. Every few rounds the engine offers two activities (`choice`: its best candidate and the best of another mechanic, else another kind, both logged with their rationale); the learner picks one (`POST /api/v1/sessions/{id}/decisions/{seq}/pick`, once, and only while it is the latest decision). Every few rounds Play shows three faces after the answer (`POST /api/attempts/{event_id}/rating`, once, skippable). Ratings and picks become a per-kind preference (shrunk towards nothing, `engagement.preferences`) that nudges the enjoyment term (weight 0.3), never the estimates: engagement is kept apart from mastery. A grown-up says "can do it" or "not yet" for a skill, as a parent or a teacher, with an optional note (`POST /api/v1/learners/{id}/overrides`, withdrawn with Undo): it sets BKT's estimate to 0.95 or 0.05 at that moment and the rounds after it move it on; it never counts as an answer, and a "not yet" is a prerequisite gap. The Learner screen's Engagement tab shows each kind's rounds, first-answer rate, typical time, tries, faces and picks, and names patterns as hypotheses with what else could explain them (quick and right, stuck, fewer right late in long sessions, the sad face, passed over); slowness alone is never one. Policy `utility@2`; `utility@1` decisions still replay, as v2 with no choices, ratings or overrides decides exactly as v1.
    - Left for later: the thresholds behind the patterns (5 rounds, 3 s, 15 s) and the preference weight are first guesses; the pilot checklist needs real sessions; ratings are asked after a round, not at a session's end; a choice is between kinds of round, not within one. The pick and face tiles are left open, as ChoiceGrid has no neutral picked state (strata-react#306).

7. **Offline answers (0.9.0, in review).** Spec §14: "client should render deterministic validated item payloads and queue events offline; server reconciles idempotently". The owner approved it on 2026-11-23.
    - Done: answers and faces wait in the browser's storage (`web/src/api.ts` `answers`, a queue named `flashtap-answers`) and are sent oldest first when the server can take them, retried after 2 s doubling to a minute and at once when the browser is back online; a face is sent after the answer it rates and not at all if that answer is refused; a refused answer (a pack changed since its round was made) is listed with the server's reason until a grown-up dismisses it. The Layout says how many wait, for the grown-up. Play does not wait for the server: it keeps rounds the server made (`GET /api/rounds`, 8 of each kind played, one request every few rounds; `web/src/reserve.ts`) and plays one when a round cannot be fetched, saying so in a quiet line. "Chosen for them" cannot ask the engine offline, so it plays kept rounds of the kinds the engine chose that visit, recorded as `asked: "offline"` in a sitting of their own (never a decision's), and asks the engine again after each. The server is unchanged in what it trusts: it judges every answer by rebuilding the round, logs it once by `event_id`, and a decision replays from what had been received by its time, so answers that land late never change a past decision (a unit test plays a session through an offline stretch and replays it exactly).
    - Left for later: the page itself does not load without the server (a service worker would need https, and the app is often on plain http at home), so offline means a page already open; a round from packs the server no longer has is refused when it lands (the server keeps only the current packs), which a long offline stretch across a deploy that raises a pack would hit; the device's clock stamps when a round was shown and answered, and is not checked.

8. **Steps of difficulty (0.11.0, in review).** From the spec check after P4: the engine chose the kind of round but the number of choices and the number range were still the grown-up's settings (§6 "shared difficulty dimensions"; §13 "rapid acceleration, regression").
    - Done: every template has a ladder of steps, easiest first (`rounds.Level`: how many options or pieces and, for Counting, Quick look, Missing, Give and Order, the largest number asked about, inside the skill's `number_range`). A round carries its step (`level`) and so does its attempt and decision (a new column on each); a round with no step is built exactly as before, so no template version was raised and every earlier attempt rebuilds. The engine keeps a staircase per kind of round from the learner's own answers (`engine/model.py` `Stair`): up after 3 first answers right in a row at a step, down after 2 missed, and a right answer at a harder step (or a miss at an easier one) moves it there; a kind not yet played starts at the easiest step, or halfway up when its skill is already known (from answers, the graph or a grown-up). After 2 misses in a row the round is one step easier. Policy `utility@4`; `utility@3` and before still replay with the grown-up's choices. The step sets the chance of a lucky answer in the prediction; the reason says when a round is a step harder or easier ("A step harder than last time: numbers to 5, 4 to pick from."). On 200 simulated learners (who slip more at harder steps) the engine's model still beats the rule (log loss 0.578 against 0.618) and learners played by the engine knew 12.8 skills at the end against 12.4 under a uniform pick.
    - Left for later: the ladders, 3-up/2-down and the halfway start are first guesses; the estimate is one per skill over every step (the spec's core capability plus parameters, §4), so a learner strong at numbers to 5 and not to 20 shows as partly known rather than as two states; rounds kept for offline play are made at the grown-up's choices, with no step; fluency (speed) and misconceptions from the distractor tapped came in 0.12.0 (item 9).

9. **Fluency and misconceptions (0.12.0, in review).** From the spec check after P4: the learner state lacked a fluency estimate and active misconceptions (§10 "fluency distribution ... confusion patterns, active misconceptions"; §16 "misconception discrimination").
    - Done: when an attempt is judged, the server stores what its first answer showed (`attempts.distractor`, the generator of the option tapped, and `attempts.traps`, each misconception a wrong option of the round could show; `src/flashtap/mistakes.py` maps a 9 for six to "Confuses 6 and 9", a d for b to "Confuses b, d, p and q", a count one or two out to "Skips or double-counts objects"). `learners/misconceptions.py` folds them per misconception: offered, wrong, shown, and how many luck alone would put there; suspected once it is shown at least twice and luck would give that many under 1 time in 20, cleared after 3 right answers in a row with it on offer. A suspected misconception holds its skills at Emerging; it moves no estimate. `learners/fluency.py`: the typical time to a right first answer per skill, from rounds in the first 10 minutes of a session and under a minute, and a trend against the learner's own earlier answers on the same kind and step; shown, never part of a state or the engine's choice (§10). Policy `utility@5` gives a round that can offer an open misconception's trap a bonus (1 suspected, 0.5 unclear) and picks a seed whose round offers it (`misconception_probe`); `utility@4` and before ignore the tally and still replay. The Learner screen shows Speed per skill, "Held back" under a state, each wrong answer in words with its time, and a Mix-ups tab. Export `flashtap-learner@6`.
    - Left for later: the thresholds (2 shown, 1 in 20, 3 to clear, 10 minutes, a minute) are first guesses; attempts from before 0.12.0 stored no traps and give no misconception evidence; placing rounds (a whole arrangement) show none yet; "Reverses teen numerals" has no kind that can offer it (numbers stop at 20); the packs' other misconceptions (letter names, added schwa, first-letter guessing, recounting, longer is more) need rounds written to show them; the simulated learners have no misconceptions, so the simulation does not exercise probes. Transfer rounds are next.

10. **Transfer rounds (0.13.0, in review).** From the spec check after P4: no transfer probes or holdout families (§9, §13 "progress when ... transfer probes pass", §16 "Transfer: novel mechanic/representation").
    - Done: twelve transfer kinds (`rounds.TRANSFER`, `Template.held_out`), one for each skill a practice kind assesses, each the same skill in another mechanic or representation (table in `docs/content.md`, "Transfer kinds"): Hear and find, Colour box, Shape box, Which group, Quick dots, One more one less, Biggest number, Number card, Small letters, Letter box, Same first sound, First sounds. They are held out of practice: Mixed and Play's list leave them out. `learners/transfer.py`: a skill's transfer answers are its counted primary answers in its transfer kind; it passes when the latest two are right; Generalised now needs independent, passed, and a right answer in a practice kind (it was "right in two mechanics"). Policy `utility@6` plays a transfer kind only as a `transfer_probe` for a skill rated known with 3 right in practice and not yet passed, else sets it aside as `held_out`; `utility@5` and before replay. The Learner screen says how each skill's check went under its state. Export `flashtap-learner@7`. A placing round now shows its `show` (Number card's numeral).
    - Left for later: one transfer kind per skill, so a learner who has passed it has no fresh held-out form left (a second family, or held-out items within a kind, would need more kinds or pack versions); a passed check is not repeated as a delayed probe; the simulated learners know a skill in every form alike, so the simulation can only show what checks cost, not what they find; the pass rule (2 in a row) and the 3 practice answers before a check are first guesses; which forms count as "the same skill" is a judgement for the teacher's review.

11. **First steps, and kinds opened by success (0.14.0, in review).** Asked for when real use began: the easiest rounds were still too hard to start on, and progression should be gradual and only on success.
    - Done: four first-steps kinds (`packs/starter.toml`, `kinds/starter.py`): Same picture, Same colour, Same letter, Same number, two tiles at the first step and never more than four, wrong tiles always unlike the right one; their transfer kinds (Picture, Colour, Letter and Number twins). Policy `utility@7` sets a kind aside (`not_yet`) until every taught skill it waits on is shown (rated known on the learner's own answers or a grown-up's "can do it"), so a new learner begins on the first steps and the rest open a shown skill at a time (docs/content.md, "First steps"); `maths.number` version 2 orders Missing number and Order after Counting. `utility@6` and before replay.
    - Left for later: the order is Flashtap's judgement (the four new edges and two in `maths.number`), for the same teacher review as the rest; Sounds opens right after Same letter, since the packs give it no taught prerequisite but knowing letters (hearing a first sound only `facilitates` it); a learner who played before 0.14.0 shows the first steps again before the kinds they had (quick for one who can, or a grown-up's "can do it" skips them).

12. **The very first rounds: numbers to five, colours, shapes and animals (0.15.0, in review).** The owner, trying it: still too hard, "what starts with letter H"; it needs to be like numbers 1-5, colours, shapes, animals.
    - Found: the deployed server was still 0.13.0 (no first steps), and Play starts on the saved kind, Mixed by default, which draws from every kind. Under 0.14.0 Sounds would have opened right after Same letter.
    - Done: Same picture shows animals only (template 2, "Same animal"); Same shape and Shape twins join the first steps (`maths.geometry.same_shape`, a judgement edge to naming shapes; `starter` pack version 2). Policy `utility@8`: every literacy kind also waits on the first words (`FIRST_WORDS`: Matching, Colours, Shapes, Counting), and every sound kind on Capitals too (`LETTERS_KNOWN`), so Same letter leaves the first steps; a known skill no longer counts the reach of the kinds still closed behind it, which had kept Same letter coming back while Capitals waited. With a learner chosen and the saved kind Mixed, Play starts on "Chosen for them".
    - Left for later: the order is the scheduler's (no source puts colours before letters), for the teacher review; Matching still draws food and vehicles as well as animals; Mixed by hand still offers every kind.

13. **A more engaging voice (0.17.0, in review).** The owner: use language model calls to write better dialogue, using the player's name, less repetitive, done in advance; and the consonants, which strata-models can now say.
    - Done: every phonics sound is made by `speak`'s `sound`. `talk.py`: a pool per moment (a cheer in place of "Yes!", another go, before the answer, a hello, a choice of two, a break, and an intro for every kind), written by the `write` role on the job queue at each start, checked line by line (`talk.check`), the nickname filled in on the server; the voice build makes every line for every learner, and a new or renamed learner queues a build. Play goes round each pool (`web/src/talk.ts`).
    - Left for later: the written lines are checked by rules, not yet by a person in the app (`flashtap talk strike` is the way to remove one); lines are per moment and kind, not per round, because the engine chooses each round from the answer before it, so no session is planned ahead; a streak ("three in a row") and the end of a session have no lines yet; a removed learner's name clips stay in the voice folder until it is cleared.
14. **On by itself, and a running score (0.18.0, in review).** The owner: once a question is done, go to the next after a short pause, counting down on the button from 3; keep a running score per learner, shown at all times, green right and red wrong.
    - Done: Next counts down (`next_after`, default 3 seconds, 0 waits for a tap; with the faces asked, from a face tapped) and plays the next round. `GET /api/learners/{id}/score`: first answers right and wrong, all time, struck ones left out; Play and Break show it as two big pills, adding each answer the moment it is kept, offline too, and taking off any the server refuses (`web/src/score.tsx`).
    - A change from the spec, by the owner's ask: §11 and §17 ask for no streak pressure and no punishment for mistakes, and Play had no score; there is still no streak, but wrong first answers are counted in red. Worth a look in the field study (P5): whether a red count puts a young learner off.
    - Then (the owner): the screen fills the window, centred, with wider padding as it grows; the answer tiles stretch and pulse one at a time at random until the round is answered, and the picture to match is a step larger. The stretching and the pulse were added to strata-react (`ChoiceGrid`/`PlaceBoard` `stretch` and `beckon`, 1.3.28), as the standing rule asks.
    - Left for later: an answer an earlier visit left waiting on the device joins the score when it lands and Play is opened again, not at once; the countdown, a hook of Play's own (`useCountdown`), could become a strata-react button if another app wants one.

15. **Ramping up on every right answer (0.19.0, in review).** The owner, watching a learner answer a few right: it should ramp far more aggressively, stepping up every time an answer is right, so it finds the current level quickly.
    - Done: policy `utility@9`. A kind's stair steps up after every right first answer and down after every miss (`model.Params.up`, `down`: 1 and 1; 3 and 2 before, `SLOW_STAIR`, which replay uses for older decisions). An open kind whose skill is not yet known gets a bonus (`Weights.ahead`), so the next thing to learn comes before more rounds of what is known. An all-right learner opens every practice kind in about 60 rounds (about 250 under `utility@8`); simulated learners know 13.86 skills after 6 sessions (13.52 with the quick stair alone, 13.46 under `utility@8`, 13.39 at random).
    - Left for later: one up and one down settles where about half the first answers at a step boundary go right; the frustration guard (an easier step after two misses, a break after three) is what keeps it kind. Watch real sessions for too many misses.

P5 (field validation) is a study, not code.

## Decisions (2026-11-23)

| Question | Decided |
| --- | --- |
| Keep the npm library and its Pages demo? | Replaced by the app (0.2.0) |
| Who plays, and where does it run? | Personal, private use, self-hosted behind a reverse proxy. The repository is public, so it holds nothing that identifies anyone (rule 8 in `AGENTS.md`) |
| Which learners? | Every school year and ability, starting with the earliest skills; progression by ability, not age (Scope, above) |
| Device and offline use? | Tablet or laptop browser; answers queued in the browser and rounds kept for when the server is away (approved 2026-11-23, 0.9.0) |
| Voice? | Pre-generated UK English clips (strata-models `speak`, voice `bf_emma`), browser speech as fallback (agreed 2026-11-23, 0.9.0). A speech model wraps a lone consonant in a vowel, so until 0.17.0 consonants were recorded by a grown-up; strata-models' `sound` (#112) now cuts each one from a carrier syllable, so every sound is made and a recording on the Sounds screen is for one that does not sound right (kept on the server, never in git); a sound with no clip is described ("the first sound in ship"). The lines around a round vary and use the learner's nickname, written ahead by strata-models' `write` role with the name filled in on the server (0.17.0). |
| Look of the Play screen? | strata-react components; what it lacks is added there ("add components to strata react as needed"). the tap tiles are strata-react's `ChoiceGrid` (1.1.5); the stand-in `styles/play.css` is gone |
| First content pack? | The earliest skills (numbers to 10, Phase 2-3 phonics) in a schema built for every year, grown per pack version |
| Pack format? | TOML instead of the planned YAML: standard library, no implicit typing; pydantic refuses unknown keys |
| Common code? | Flashtap uses strata-python and strata-react for everything they offer, and what they lack is raised there as an issue (standing rule, 2026-11-23). The API's TypeScript types are generated by strata-react's `strata-api-types` from the schema strata-python's `openapi` command writes. strata-python 0.2.12 and strata-react 1.3.7 (the answer queue, #308) are used, with no stand-ins left (progress log, 2026-11-24) |
| Where does data live? | `strata_python.db`: SQLite in tests, the app's schema on the shared Postgres when deployed; never in git. With no database configured, a SQLite file beside the settings (so an install records with nothing set up) |
