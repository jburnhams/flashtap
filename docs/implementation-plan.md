# Implementation plan

From a one-mechanic game to the adaptive learning spec (v0.1, 2026-11-17, written for the early years; "Technical design specification": ontology, seeded items, mechanics, evidence, learner model, scheduler, P0 to P5 roadmap). The full plan, with the gap analysis and the decisions it needs, was written 2026-11-22 with the owner; this is its working copy. Section numbers (§) are the spec's.

Scope (decided 2026-11-23): every school year and ability, starting with the earliest skills but not limited to them. Progression is by ability, not age: the skill graph's prerequisites and the learner's evidence decide what comes next; curriculum stages (EYFS, KS1 to KS4) are labels mapped onto skills, never gates; placement is by probes; no age, birth date or year group is stored.

## Where Flashtap stood (0.1.9)

One mechanic (tap one of N pictures), five unseeded round types, no learner state, a points-and-streak score, in the browser only. Bugs against §9: Colours could offer two right answers, Counting hung above ten choices, every tile printed its own name (so Letters and Colours were reading tasks), Letters mixed /k/ and /tʃ/ under C, and sentences were built from string templates ("How many Sheeps").

## PRs

1. **Migrate (0.2.0, done).** python-app-template shape; seeded, checked rounds in Python with the five bugs fixed; `GET /api/round`; Play and Settings on strata-react; no score or streak.
    - Exit: property tests over thousands of seeds per mode find exactly one right option, and the same seed gives the same round.
2. **P0 ontology seed (0.3.0, done).** `src/flashtap/packs/` as versioned TOML (not YAML: `tomllib` is in the standard library, so no new dependency) with pydantic models ([content.md](content.md)): skills, parameter dimensions, typed edges with provenance (§3), misconceptions, curriculum objectives. The schema covers every school year (skills, not ages; stages only as curriculum labels); the first slice to fill it is the earliest skills: maths counting, cardinality, subitising 1-5, numerals 0-10, more/fewer; literacy letter forms, initial sounds, Phase 2 GPCs (s a t p i n m d). `flashtap content check` refuses dangling edges and `prerequisite_strong` cycles. An adult Content screen.
    - Exit: every EYFS maths and literacy Early Learning Goal is mapped or marked out of scope, and a skill from a later stage can be added without a schema change.
    - Done: 44 skills over 3 domains and 20 strands, 52 typed edges, 9 misconceptions, Letters and Sounds Phases 2 and 3 (51 GPCs), 71 words with their sounds (the old `lexicon.py` tables moved here); 15 EYFS goal statements, 12 mapped and 3 set aside (retelling, letter formation, free writing); a test adds a Key Stage 1 skill and objective with no schema change. Every pack is a draft until reviewed: the IPA and segmentations by a phonics teacher, the edges marked `src.flashtap_judgement` by someone who teaches early maths and reading.
3. **P1 mechanics (0.4.0, done).** Templates declare Q-matrix roles (§7, §8). Mechanics: select one, match pairs, sort, sequence, give-N, fill missing, brief exposure, audio respond. Distractor generators: near-number, reversal (6/9, 12/21), confusable graphemes (b/d/p/q), phonological neighbour.
    - Exit: every item rebuilds from (template, version, seed); the validator suite over 1,000 seeds per template finds no ambiguous key.
    - Done: 12 templates over the 8 mechanics (`rounds.TEMPLATES`; the 5 original kinds plus Missing number, Quick look, Listen, Give a number, Order, Capitals, Sort by sound), each with a version and its skills as primary, secondary or confound. A round carries (kind, version, choices, seed) and the versions of the packs it drew from (`content`, recorded on every attempt and decision since 0.7.0) and rebuilds from them; another template or pack version is refused, not answered differently. `mechanics.check` covers both families: one tap (one right option, distinct pictures, every wrong option names its generator) and an arrangement (each piece belongs in at most one place, pieces that look alike belong together, every place can be filled). `test_rounds.py` walks 1,000 seeds of every template. The placing board is strata-react's `PlaceBoard` (strata-react PR #285, released as 1.3.0), two taps rather than a drag, because React Aria's drag and drop has no tap-to-hold state for small fingers.
    - Left for later: the confusable and neighbour tables are drafts for the phonics review; a Quick look's 1.5 s is a default, not a measured threshold; audio respond says a whole word with the browser's voice, and isolated sounds wait for recorded clips.
4. **P2 learner baseline (0.5.0, done).** `strata_python.db`: learners (pseudonymous id plus a nickname; no age, birth date, year group, school or photo), sessions, append-only attempt events keyed by `event_id`, tombstones. Rule and BKT estimators behind one interface (§10); derived reporting states (§13), unobserved kept apart from not mastered. Adult Learner screen with evidence provenance; export and delete (§17).
    - Exit: rebuilding from the event log reproduces identical estimates.
    - Done: `src/flashtap/learners/` (models, store, evidence rules, estimators, report) and its first migration; the server rebuilds each attempt's round and judges the first answer itself; a resent event is acknowledged once, a changed one refused. Estimates are never stored: they are computed from the log on read, so the profile is a rebuild every time, and `flashtap learners rebuild <export>` checks an export's estimates against its own events (a unit test replays 60 attempts, and the same attempts sent in another order, to identical estimates; an integration test does it through a real server and a real `flashtap` process). Play records rounds for the learner chosen in Who is playing; the Learners and Learner screens show each skill's state, BKT beside the rule baseline, and the rounds behind it with why each did or did not count; strike out with Undo, export, delete behind a confirm. With no database configured the records go in a SQLite file beside the settings.
    - Left for later: BKT's prior, learn, slip and guess (1 in the number of tiles) and the state thresholds are first guesses, to be fitted from real attempts in P3; fluency and retention estimates (§10) wait for P3's scheduler, which needs them; overrides by a grown-up (`POST /v1/learners/{id}/overrides`, §15) are not built; attempts are sent once from the browser (no offline queue yet: a round the server did not take says so and is lost); the deployment still needs its Postgres schema (`strata-db new-app flashtap` and the service's `STRATA_DB_*` environment, see [deploying.md](deploying.md)).
5. **P3 adaptive engine (0.6.0, in review).** `POST /api/v1/sessions` and `/next` with rationale codes (§15). Eligibility filters, utility ranking, seeded exploration, logged candidates and probabilities (§12). Placement by probes from the learner's evidence (never from an age), spaced review, diagnostic contrasts, a session length cap and offered breaks. Replay endpoint.
    - Exit: on simulated learners, held-out log loss beats the rule baseline.
    - Done: `src/flashtap/engine/`. The model is BKT over the skill graph's strong prerequisites (closed through skills no round assesses yet): a right primary answer lifts unseen prerequisites, a wrong one caps unseen dependents, so a few probes place a learner; a round is predicted from every skill it names. The policy puts limits first (20 rounds or 15 minutes, a break offered every 10 rounds and after 3 misses running), then weighs one candidate per kind of round, labelled placement probe, introduce, practise, spaced review (a per-skill half-life) or consolidate, set aside for a known prerequisite gap, after 2 misses unless likely to go right, or after the same kind twice; it ranks them by learning, information, retention, enjoyment, frustration, repetition and a diagnostic bonus for a contrast after a miss, and draws by a softmax with 10% uniform, seeded by the session and decision number. Every decision is stored (`decisions` table) with every candidate's components and chance; `/next {seq}` is idempotent; `POST /api/v1/evaluations/replay` and `flashtap learners rebuild` remake each from the log as it stood (receipt and strike times) and name any that differ. Play has "Chosen for them" with the reason shown, break offers and the session's end. On 200 simulated learners (6 sessions each, fitted on 140, scored on 60 held out), the engine's model has log loss 0.522 against the rule's 0.556 (Brier 0.173 against 0.187); BKT without the graph is between, 0.528. Learners played by the engine policy knew 12.8 of 18 skills at the end against 12.5 under a uniform pick.
    - Left for later: the weights, thresholds and caps are starting points to fit from real sessions (each decision's logged chances make an off-policy comparison possible); the cap and break interval become the grown-up's settings in P4; difficulty within a kind (choices, number range) is still the grown-up's setting, not the engine's; the simulation's learners are a model, so its numbers say the code works as designed, not that children learn (P5); retention does not yet change the prediction, only the schedule, until delayed answers say how much is forgotten; transfer probes (§13) wait for a second template per skill; overrides by a grown-up are still not built.
6. **P4 engagement, light.** Choice of two activities, a 3-point face rating, hesitation and retry patterns shown as hypotheses (§11), parent session limits.
    - Exit: a short pilot checklist; it needs real sessions.

P5 (field validation) is a study, not code.

## Decisions (2026-11-23)

| Question | Decided |
| --- | --- |
| Keep the npm library and its Pages demo? | Replaced by the app (0.2.0) |
| Who plays, and where does it run? | Personal, private use, self-hosted behind a reverse proxy. The repository is public, so it holds nothing that identifies anyone (rule 8 in `AGENTS.md`) |
| Which learners? | Every school year and ability, starting with the earliest skills; progression by ability, not age (Scope, above) |
| Device and offline use? | Tablet or laptop browser; attempts queued in the browser later (recommended answer, not yet discussed) |
| Voice? | Pre-generated UK English clips (strata-models `speak`), browser speech as fallback (recommended answer, not yet discussed) |
| Look of the Play screen? | strata-react components; what it lacks is added there ("add components to strata react as needed"). the tap tiles are strata-react's `ChoiceGrid` (1.1.5); the stand-in `styles/play.css` is gone |
| First content pack? | The earliest skills (numbers to 10, Phase 2-3 phonics) in a schema built for every year, grown per pack version |
| Pack format? | TOML instead of the planned YAML: standard library, no implicit typing; pydantic refuses unknown keys |
| Common code? | Flashtap uses strata-python and strata-react for everything they offer, and what they lack is raised there as an issue (standing rule, 2026-11-23). The API's TypeScript types are generated by strata-react's `strata-api-types` from the schema strata-python's `openapi` command writes. strata-python #36-#41 (0.2.6) and strata-react #293-#299 (1.3.3) are released and used, with no stand-ins left (progress log, 2026-11-23) |
| Where does data live? | `strata_python.db`: SQLite in tests, the app's schema on the shared Postgres when deployed; never in git. With no database configured, a SQLite file beside the settings (so an install records with nothing set up) |
