# Repository Guidelines

This file is for people and coding agents (`CLAUDE.md` imports it). It follows the same file in [python-app-template](https://github.com/jburnhams/python-app-template), which Flashtap is built from: the sections and every rule that holds for every app are kept as the template has them, so template updates can be merged in; the descriptions are Flashtap's.

## What this is

Flashtap: tap-the-right-picture rounds for every school year and ability, starting with the earliest skills (twelve kinds of round over eight mechanics today: tap one picture, fill the missing number, a quick look, listen for a letter, give a number, put in order, match pairs, sort), progressing by ability, never by age. A Python backend (FastAPI + CLI) owns the rounds and their answers (templates in `rounds.py` over the mechanics in `mechanics.py`, seeded, versioned and checked, over the words in the content packs, `src/flashtap/packs/*.toml`, read and checked by `content/`), the learner records (`learners/`: learners by nickname, append-only attempt events judged by the server, tombstones, rule and BKT estimators and derived reporting states, on `strata_python.db`) and the adaptive engine (`engine/`: what to play next and why, from the learner's evidence over the skill graph, every decision logged with its candidates and chances and replayable, including choices of two activities; scored on simulated learners by `flashtap engine simulate`), and engagement (`learners/engagement.py`: face ratings, picks and a grown-up's overrides, kept apart from what the learner knows, and patterns named as hypotheses); a React frontend built on [strata-react](https://github.com/jburnhams/strata-react) (TypeScript + Vite + Tailwind CSS v4) only shows them and reports taps and arrangements. Hermetic unit and integration test suites, Storybook, screenshot tests, coverage ratchets and multi-OS GitHub Actions CI. Where it is heading is `docs/implementation-plan.md`.

## Rules for every change

1. **Run `scripts/check` before every commit** (`--fast` skips the tests, `--fix` applies ruff). CI runs the same steps. Never skip, disable or quarantine a test or a check to get green.
2. **Keep the docs and the changelog in the same commit as the change**: add an entry to `CHANGELOG.md` (newest day first; a bold one-line title, what was asked, then bullets naming each file touched and what changed; say **new** for new files, and call out corrections to earlier claims), and update the README, this file and `docs/` where they stop being true.
3. **Write the why**: dense code with comments that say why, not what. Facts, commands, paths and decisions; link instead of repeating what another doc or upstream page already says.
4. **No secrets, no machine-specific details** in this repo. Say where a secret lives (an environment variable name, a password manager), never its value. Hostnames, addresses, user names, local paths and the owner's infrastructure belong in the owner's private docs, not here: examples use placeholders (`/home/ada/...`, `<port>`).
5. **Types are not optional**: everything in `src/` is fully annotated and passes `pyright` (strict) and `ty`; a new file is strict from its first commit. Style is `ruff format` at line length 120, not by hand.
6. **Tests come with the change**: unit tests for logic, integration tests for the CLI and HTTP API, web tests and stories for screens. Coverage floors only ratchet up.
7. **Say what you ran**: in the PR or the final message, list the commands you ran and their results, and name what you could not run.
8. **Nothing that identifies a person, above all a child.** Flashtap is for private use but this repository is public. No real names, nicknames, ages, birth dates, year groups, schools, places, photos, voice recordings, learner data or exports, in code, fixtures, tests, stories, screenshots, docs, commit messages or PRs. Test and story learners are invented ("Learner A", "Fox"). People are "the owner" or "a learner", never named; the one exception is the copyright holder in `LICENSE`, which the licence needs. Learner records exist only in the deployed database, under a nickname chosen there, and the learner model stores no age: what comes next is decided by evidence of ability.

## Layout and conventions

- Shared server code is the [strata-python](https://github.com/jburnhams/strata-python) library (read its `AGENTS.md`): `oslib`, the `Settings` class, `web.base_app`/`add_web`/`with_base`/`serve`, the `doctor`/`set`/`serve` CLI commands, the pytest plugin and the `strata-check` gate. Do not copy those modules into the app; if the library lacks something every app needs, change it there. This repo only declares its settings (`settings.py`), its own routes (`server/app.py`) and its own commands (`cli.py`).
- Content (skills, edges, phonics, words, curriculum mappings) is TOML in `src/flashtap/packs/`, checked by `flashtap content check` and at server start; read `docs/content.md` before changing a pack, raise its `version`, and keep it `status = "draft"` until someone who teaches it has checked it. Skills never carry an age or year group: stages are curriculum labels only.
- Learner records (`src/flashtap/learners/`) hold a random id and a nickname per learner and the rounds they answered, nothing else; estimates are computed from the attempt log on every read, never stored, so they rebuild exactly (`flashtap learners rebuild <export>`). The models are `learners/models.py`, the migrations `src/flashtap/migrations/` (inside the package, so an installed wheel migrates at start); `src/flashtap/strata-db.toml` names both (inside the package, so an installed wheel finds it with `Project.load(__file__)`; `[tool.strata-db] file` in `pyproject.toml` points strata-db and the pytest plugin at it). The server opens the database on the first request that needs it (`strata_python.db.web.add_database`, `DbSession`). A model change needs a reviewed revision (`uv run strata-db revision -m "..."`) in the same commit; `tests/unit/test_database.py` checks it.
- Python application code lives in `src/flashtap/`; the React web app lives in `web/src/` and builds into `src/flashtap/server/static/`, which `flashtap serve` serves at every non-API path.
- The API's TypeScript shapes are generated, not written: `web/src/api.ts` names them from `api.generated.ts` (`Schema<'Round'>`) and only narrows what the schema cannot say. A shape the web app needs comes from a typed pydantic model on the server.
- The web app follows strata-react's rules (its `CLAUDE.md`, "Building an app on Strata"): only Strata components and theme roles (no raw palette colours, arbitrary values or `dark:` overrides), every remote read `useLoad`/`useInfiniteLoad` → `DataView`/`InfiniteList` with skeleton and empty state, one filled button per view at a time (the `BulkBar` action takes it while rows are chosen), reversible removals through `useUndoable`, URL state for sort/tab and choices (`useSearchParam`, `NativeSelect param=`), navigation as `ButtonLink`/`TextLink`, speech through `speak`/`SayAgain`, numbers and dates through `format`. Each screen in `web/src/screens/` opens with its one question. Something Strata lacks is added to strata-react (a component with its story and tests there), not hand-built here; until its release lands, a stand-in here is kept small and named in `docs/implementation-plan.md`.
- Cross-platform (Linux, macOS, Windows): OS differences (file locks, process liveness and termination, priority, how to start the CLI) live in `strata_python.oslib`; do not import `fcntl` or call `os.kill(pid, 0)` elsewhere (on Windows that terminates the process).
- Reverse-proxy support: the server gives every page a relative `<base href>` back to its root (`with_base` in `server/app.py`), the web build uses relative asset paths (`base: './'` in `vite.config.ts`), and strata-react's `appBase()` reads the page's base URL; it is React Router's `basename` (`web/src/main.tsx`). Every request goes through the typed client in `web/src/api.ts` (`createTypedApi`, which adds the base); any other URL the app builds for `<img>` or a download must go through strata-react's `withBase`; in-app links are router paths.
- Docs live in `docs/`: `overview.md` (design brief), `content.md` (content packs: format, rules, what is left to review), `implementation-plan.md` (milestones and next steps), `progress.md` (log of findings and decisions), `deploying.md` (running it as a service; keep it generic), `prompts/` (unattended agent prompts for backend unit, integration and web tests).

## Python tooling (uv)

- `uv sync` builds `.venv` from the committed `uv.lock`; `uv run <cmd>` runs inside it; `uv add <pkg>` / `uv add --group dev <pkg>` change dependencies (commit `pyproject.toml` and `uv.lock` together). Version, dependencies, the `flashtap` entry point and every tool's configuration are in `pyproject.toml`; the version lives only there (`flashtap.__version__` reads it back). `./flashtap` and `flashtap.cmd` are thin wrappers for `uv run flashtap`.
- `scripts/check` is `uv run --locked strata-check` (from strata-python): `uv lock --check`, `ruff check`, `ruff format --check`, `pyright` and `ty`, then the unit tests with coverage. Options such as the checked paths are in `[tool.strata-check]` in `pyproject.toml`.
- strata-python comes from PyPI (`strata-python>=0.2,<0.3`); `uv.lock` pins the release and Dependabot proposes new ones. `uv lock --upgrade-package strata-python` picks up a release at once.
- `uv run pytest tests/unit --cov` runs the unit suite with coverage (random order via pytest-randomly; `-n auto` runs in parallel; `diff-cover` checks the lines a change touches). `uv run pytest tests/integration -n auto` runs the integration suite.
- `uv run flashtap doctor` checks the environment; `uv run flashtap round --mode counting --seed 7` prints one round (`--json` for the API's shape); `uv run flashtap content check` checks the packs (`content list` prints the skills); `uv run flashtap learners list` lists the learners and `learners rebuild <export.json>` checks an export's estimates against its own events; `uv run flashtap openapi` (strata-python's shared command; `--check` compares) writes `web/openapi.json`, the server's schema the web app's types are generated from (run it, then `cd web && npm run api-types`, whenever a response model changes; a unit test fails until you do); `uv run flashtap set choices 6` changes a setting; `uv run flashtap serve` runs the web server on port 8361.
- Python coverage is calculated from the unit suite only (`fail_under` in `pyproject.toml`).
- Style: pytest style tests (`def test_...` with `assert`; use `monkeypatch`/`tmp_path` instead of patching globals by hand).

## Testing policy

Prefer real code over mocks. A test that runs the real thing finds the bugs that matter; a mock only proves the code agrees with the test.

- **Real by default**: real HTTP requests (against a real local server: the `http_server` fixture from the strata-python plugin, or its `live_app` fixture to run the app itself on a loopback port), real embedded databases (SQLite, or the Postgres service container, via the database project's `db_session` fixtures; see Database), real files in `tmp_path`, real subprocesses. In the web app that means MSW answering real `fetch` calls, never a stubbed `fetch` or a mocked module.
- **Mocks and fakes are the exception**: use one only for a true external (a paid or remote service, hardware, the clock) and only in quick unit tests that cover many cases where speed is the point. Never mock your own modules or the database. Even then, keep one test of the same path against the real thing.
- **Install what the tests need**: CI runners can have software installed. If code calls `ffmpeg`, install it (locally and in the workflow) and run it; do not mock it or skip when it is missing. Add the install to the workflow and say so in the README.
- **No silent skips, no swallowed errors**: a test must not pass or skip because something was missing or an exception was caught. `pytest.importorskip` is banned (ruff). A test is skipped only deliberately: a marker or `skipif` with a **reason** and an explicit switch, for example a 12 GB model that is too large for CI is `@pytest.mark.skipif(not os.environ.get("RUN_LARGE_MODEL"), reason="needs the 12 GB model; set RUN_LARGE_MODEL=1")` and runs on the machine that has it. Skips show in the summary (`-ra`); any new skip is mentioned in the PR.
- **Where tests need a lot of machine** (GPU, large models), mark them (`slow`, `gpu`), run them where that machine exists, and keep the marker documented in `tests/README.md`.

## Python tests

- Tests live under `tests/`, grouped by type:
  - `tests/unit/`: fast, isolated tests of pure logic and mocked boundaries (synthetic data, fakes). No external processes or network.
  - `tests/integration/`: end-to-end tests that run the CLI (in-process and as a subprocess) and the FastAPI HTTP API over real on-disk state.
  - `tests/utils/`: shared helpers (none yet; last-resort doubles for the outside world come from `strata_python.testing`). The strata-python pytest plugin (configured by `strata_env_prefix` and `strata_tuning_vars` in `pyproject.toml`) makes every suite hermetic (isolated home and data dir, no network) and provides the `http_server` and `live_app` fixtures; `tests/conftest.py` holds the rest.
- Read `tests/README.md` before writing any Python test: fixtures, conventions, file-ownership rules and the per-module coverage ledger.

## Web

- Web tests live in `web/tests/{unit,integration,utils}` (vitest; unit runs in node, integration in jsdom through `renderRoutes` from `strata-react/testing`). Backend calls are answered by msw from `web/src/mocks/handlers.ts` (every endpoint the app calls needs a handler there; the same handlers serve Storybook and the visual suite); read `web/tests/README.md` before writing any. Stories live in `web/stories/`; visual baselines in `web/tests/visual/baselines/`.
- Commands, from `web/`: `npm install`, `npm run dev` (proxies `/api` to `flashtap serve` on 8361), `npm run build` (writes into `src/flashtap/server/static/`), `npm run typecheck` (TypeScript 7, installed as `typescript7`; `typescript` is the TypeScript 6 package openapi-typescript and Storybook need, as in strata-react), `npm run api-types` (writes `src/api.generated.ts` from `openapi.json` with strata-react's `strata-api-types`; never edit either by hand, and CI runs it with `--check`), `npm run test:unit` (node), `npm run test:integration` (jsdom + msw), `npm run test:coverage:gate` (unit + integration together, what CI gates on: floors in `web/coverage-floor.json`, read by `web/vitest.gate.config.ts`), `npm run test:coverage` (unit only, informational), `npm run test:coverage:all` (unit + integration, no gate), `npm run storybook`, `npm run build-storybook`, `npm run test:visual` (builds the app and Storybook, then `strata-visual` compares every story and route state, light and dark, with the baselines), `npm run test:visual:update` (look at the diffs in `tests/visual/output/` first, say in the PR which baselines changed and why). Node 26 (`.nvmrc`). The web floors only ratchet up.

## Database

Flashtap's learner records use `strata_python.db` (strata-python's `db` extra: the shared-database library that took over from `omarchy_db`, same rules: one shared Postgres, one schema per app, SQLite in tests); see `src/flashtap/learners/db.py` for where the records go when no database is configured. The template's text follows. The template ships no database (the sample keeps JSON files in the data folder). When an app needs one, use the shared database project, [`jburnhams/database`](https://github.com/jburnhams/database) (library `omarchy_db`), not an ad-hoc `sqlite3` file or a database of its own. Follow its [adoption guide](https://github.com/jburnhams/database/blob/main/docs/ADOPTING.md) and do not restate it here; the rules that matter to an agent:

- One shared database, one schema per app. Never one database per app: Postgres cannot join across databases.
- The app's models (typed SQLAlchemy records from `omarchy_db.make_base()`) and its Alembic migrations live in this repo; the library and `dbtool` come from the database project. Add it with a git source in `pyproject.toml` (`[tool.uv.sources]`, see the guide) so CI can resolve it, and commit `uv.lock`.
- Models stay portable (generic SQLAlchemy types, a `server_default` on new NOT NULL columns) unless the app really needs Postgres features; then set `engine = "postgres"` in `[tool.omarchy-db]`.
- Every model change comes with a reviewed migration (`dbtool revision -m "..."`; autogenerate sees a rename as drop + add). CI runs `dbtool check`; tests use the plugin's `db_session` fixtures, never a mocked connection. If CI needs Postgres (pgvector, say), run it as a service container.
- Run migrations at app start (`Project.load(__file__).upgrade(engine)`) or with `dbtool migrate`.
- Connection settings come from the environment (see the guide); never put a URL with credentials in the repo.
- For data that is personal (photos, people, children) keep it out of git and behind a login.
- A worked example in this family: [bright-horizons](https://github.com/jburnhams/bright-horizons) (`src/bright_horizons/db/`, `migrations/`).
- If the database project lacks something an app needs, raise it as an issue there instead of working around it here.

## CI

`.github/workflows/unit.yml` (`strata-check --fast` once, then unit tests with coverage on Linux Python 3.11-3.13, macOS and Windows; `strata-public-check` on the tree, with the repository's own `deny` patterns for an age or a birth date in `[tool.strata-public-check]`; web typecheck, API types `--check`, coverage gate, build, Storybook build; visual regression) and `integration.yml` (integration tests on Linux, macOS and Windows, web component tests, a weekly dependency audit, weekly and on demand). `update-visual-baselines.yml` (manual) rewrites the visual baselines on the CI runner for a branch, which is how a Dependabot browser or icon bump gets new baselines. `.github/dependabot.yml` keeps uv, npm and Actions dependencies current. CI installs with `uv sync --locked`, so a stale lockfile fails the build.

## Before you say it is done

`scripts/check` passes, the integration suite passes, the web checks you touched pass (`typecheck`, `test:coverage:gate`, `test:visual` for any UI change), the changelog has its entry, and the docs match the code. Report the commands and their results.
